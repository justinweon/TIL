# 0908 TIL | 서브쿼리와 Supabase, 트랜잭션의 출발점

조회 조건을 미리 아는 경우에는 값을 직접 적으면 됩니다. 하지만 ‘평균보다 큰 주문’이나 ‘주문이 없는 회원’을 찾으려면 다른 조회 결과를 조건으로 써야 해요. 서브쿼리는 이런 질문을 SQL 안에서 표현하는 방법입니다. 이어지는 Supabase 메모는 그 SQL과 테이블을 어디에서 관리하는지로 연결됩니다.

## 1. 서브쿼리는 다른 질의 안에 들어가는 질의예요

서브쿼리는 SQL 문 안에 포함된 질의입니다. 바깥 문장을 외부 쿼리, 그 안의 질의를 내부 쿼리라고 부릅니다. `SELECT` 안에서 자주 보지만 `UPDATE`, `DELETE` 등의 문에서도 사용할 수 있어요.

원문은 위치와 반환 형태, 상관 여부를 한 분류처럼 설명하고 있어 구분이 필요합니다. ‘어디에 쓰였는가’, ‘어떤 형태를 반환하는가’, ‘외부 행을 참조하는가’는 서로 다른 기준이에요.

| 구분 | 의미 |
|---|---|
| 스칼라 서브쿼리 | 한 열, 최대 한 행을 반환해 하나의 값처럼 쓰입니다. 행이 없으면 NULL, 여러 행이면 오류가 납니다. `SELECT` 목록뿐 아니라 값 표현식이 가능한 곳에 쓸 수 있어요. |
| 인라인 뷰·파생 테이블 | `FROM` 안의 서브쿼리 결과를 테이블처럼 조회합니다. 실제 임시 테이블 객체를 생성하는 것은 아닙니다. |
| `WHERE` 서브쿼리 | 계산한 값을 비교하거나 `IN`, `EXISTS` 등으로 조건을 판단합니다. 위치를 설명하는 이름이에요. |
| 상관 서브쿼리 | 내부 쿼리가 외부 쿼리의 열을 참조합니다. 반드시 `WHERE`에만 있어야 하는 것은 아닙니다. |

> 바로잡기: 내부 쿼리 결과를 외부에서 사용한다는 사실만으로 ‘상관’이라고 부르지는 않아요. **내부에서 외부 행의 값을 참조하는지**가 기준입니다. 또 ‘내부 쿼리가 항상 먼저 한 번 실행된다’는 설명은 실제 실행 순서를 보장하지 않습니다. 상관 관계와 옵티마이저의 실행 계획에 따라 처리 방식이 달라져요.

원문에는 완성된 SQL 예제가 없으므로, 아래 코드는 개념을 연결하기 위해 보충한 예시입니다. `members(id)`와 `orders(id, member_id, amount)`가 존재한다고 가정하며 실제 스키마를 확인하거나 SQL을 실행하지 않았습니다.

```sql
-- 평균을 한 값으로 받아 비교하는 비상관 스칼라 서브쿼리입니다.
SELECT id, amount
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);

-- 조회 결과를 FROM에서 테이블처럼 쓰는 인라인 뷰입니다.
SELECT totals.member_id, totals.total_amount
FROM (
    SELECT member_id, SUM(amount) AS total_amount
    FROM orders
    GROUP BY member_id
) AS totals;
```

평균 집계는 한 값을 반환하므로 비교식에 사용할 수 있어요. 반면 여러 주문 금액을 그대로 반환하는 질의를 단일 값 비교식에 넣으면 행 수에 따라 오류가 날 수 있습니다. 인라인 뷰는 여러 행·열의 결과를 받아 바깥에서 다시 조회할 수 있습니다.

## 2. IN과 EXISTS는 묻는 내용이 달라요

`IN`은 값이 결과 집합에 포함되는지 묻고, `EXISTS`는 조건을 만족하는 행이 하나라도 있는지 묻습니다. 회원별 주문 존재 여부는 상관 서브쿼리로 표현하기 좋습니다.

```sql
SELECT m.id
FROM members AS m
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.member_id = m.id
);
```

내부의 `o.member_id = m.id`가 외부 회원 행을 참조하므로 상관 서브쿼리입니다. `SELECT 1`의 숫자를 결과로 모으려는 것이 아니라, 조건에 맞는 행의 존재를 확인하려는 코드예요.

> 바로잡기: SQL 키워드는 원문의 `exist`가 아니라 `EXISTS`입니다. `EXISTS`는 존재가 확인되면 더 찾을 필요가 없을 수 있지만, 항상 `IN`보다 빠르다고 단정할 수는 없어요. `IN`도 반드시 모든 결과를 별도로 전부 가져와야 하는 것은 아니며, 인덱스·자료 분포·실행 계획에 따라 성능이 달라집니다.

## 3. NOT IN에서는 NULL이 결과를 바꿀 수 있어요

NULL은 단순히 특별한 문자열이나 0이 아닙니다. 값이 알려지지 않았다는 상태이므로 비교 결과가 TRUE나 FALSE 대신 UNKNOWN이 될 수 있어요. `WHERE`는 TRUE인 행만 남깁니다.

예를 들어 어떤 회원 ID가 서브쿼리의 어느 값과도 일치하지 않더라도, 그 결과에 NULL이 섞이면 `NOT IN`을 확정적으로 TRUE라고 평가할 수 없습니다. 그래서 원하는 ‘주문이 없는 회원’이 나오지 않을 수 있어요.

```sql
-- NULL을 제외한 집합과 비교합니다.
SELECT id
FROM members
WHERE id NOT IN (
    SELECT member_id
    FROM orders
    WHERE member_id IS NOT NULL
);

-- 존재하지 않음을 직접 묻는 대안입니다.
SELECT m.id
FROM members AS m
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.member_id = m.id
);
```

두 예시는 `members.id`가 NULL을 허용하지 않는 식별자라는 전제입니다. 바깥 값도 NULL일 수 있으면 두 방식의 의미가 달라질 수 있어요. `NOT EXISTS` 역시 NULL을 같은 값으로 취급하는 특별한 비교를 자동 제공하는 것은 아닙니다.

## 4. Supabase에서 구조와 데이터를 관리하는 위치

Supabase는 PostgreSQL 데이터베이스와 인증·API 등의 기능을 제공하는 플랫폼입니다. SQL은 데이터베이스를 다루는 언어이고, Supabase의 편집 화면은 그 언어와 데이터를 다루는 인터페이스예요. DBeaver 같은 DB 도구와 일부 작업이 겹치지만 같은 제품은 아닙니다.

| 메뉴 | 원문에 적힌 역할 |
|---|---|
| Table Editor | 테이블과 행을 화면으로 보고 편집합니다. |
| SQL Editor | SQL 문을 작성하고 실행합니다. |
| Database | 테이블·관계·확장 기능 등 데이터베이스를 관리합니다. |
| Authentication | 가입·로그인 등 인증을 관리합니다. |
| Project Settings | 프로젝트 URL, API 키와 접속 설정을 확인합니다. |

원문에는 `Supabase URL`, `publishable key`, `anon key`라는 설정 이름만 있습니다. 실제 접속 값은 이 문서에 넣지 않았고 설정을 조회하지도 않았어요.

보충해서 구분하면 프로젝트 URL은 어느 프로젝트로 요청할지 정하고, publishable 키나 기존 anon 키는 프로젝트 API 접근 설정에 사용합니다. 이것만으로 특정 사용자로 로그인되는 것은 아닙니다. 사용자 인증과 데이터 접근 권한은 별도로 다뤄야 해요. 공개 클라이언트용 키도 적절한 데이터 권한 정책이 전제이며, 비밀 키·관리자용 키를 공개 코드에 넣어서는 안 됩니다.

## 5. UUID와 무결성은 서로 다른 문제를 다뤄요

원문에서는 기본 식별자를 쉽게 예측할 수 있어 UUID(Universally Unique Identifier)를 사용한다고 적었습니다. 무작위 기반 UUID는 연속 증가 번호보다 추측하기 어려운 식별자를 만들 수 있어요. 다만 UUID 버전에 따라 시간 등의 정보가 포함될 수 있고, UUID라는 이름만으로 모든 값이 비밀이 되는 것은 아닙니다.

> 바로잡기: UUID는 접근 권한 검사 대신 사용할 수 없습니다. 다른 사용자의 행 ID를 알더라도 접근하지 못하도록 별도의 인가가 필요해요. 유일성도 애플리케이션의 기대에만 맡기지 않고 `PRIMARY KEY`나 `UNIQUE`로 강제해야 합니다.

키는 행을 조회할 때 자주 쓰지만, 기본키의 역할은 유일한 식별을 보장하는 데 있습니다. 이날 다시 나온 무결성은 다음처럼 연결됩니다.

- 도메인 무결성은 자료형, `CHECK`, `NOT NULL` 등으로 허용되는 값을 정합니다.
- 개체 무결성은 기본키의 중복과 NULL을 막습니다.
- 참조 무결성은 외래키가 존재하는 대상을 가리키도록 합니다. NULL 허용 여부는 별도 규칙이에요.

자료형만 정하면 모든 업무 규칙이 충족되는 것은 아니에요. 예를 들어 정수형 수량에 음수가 들어가면 안 되는 경우에는 추가 제약이 필요합니다.

## 6. 여러 변경을 묶기 위한 ACID

원문의 마지막은 TCL에 들어가기 전 ACID를 소개합니다. `Atomicity`, `Consistency`, `Isolation`, `Durability` 네 이름과 ‘원자성은 모두 성공 또는 모두 실패’라는 설명이 있고, 나머지 상세 설명은 비어 있어요.

연결을 위한 짧은 보충으로, 트랜잭션은 여러 변경을 하나의 작업 단위로 다루게 해줍니다. 주문 생성과 재고 차감을 묶었다면 일부만 남는 상태를 피하고 싶은 상황이에요.

| 원칙 | 보충 설명 |
|---|---|
| 원자성 | 트랜잭션의 변경을 모두 반영하거나 모두 취소합니다. |
| 일관성 | 정해진 무결성 규칙을 만족하는 상태 사이에서 작업이 완료되도록 합니다. 업무 로직도 올바르게 작성해야 해요. |
| 격리성 | 동시에 진행하는 트랜잭션의 관찰·간섭 범위를 제어합니다. 실제 보장은 격리 수준에 따라 달라져요. |
| 지속성 | 커밋이 성공한 변경을 장애 이후에도 유지하도록 합니다. |

이 설명은 원문의 빈칸을 실제 강의 기록처럼 채운 것이 아니라, 네 이름을 이해하기 위한 보충입니다. 구체적인 수동 트랜잭션과 잠금 설명은 이 날짜 원문에는 없습니다.
