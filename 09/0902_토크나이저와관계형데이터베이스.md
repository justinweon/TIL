# 0902 TIL | 토크나이저와 관계형 데이터베이스

모델에 문장을 넣거나 데이터베이스에 회원 정보를 저장할 때는 먼저 표현 방식을 정해야 해요. 자연어 모델에는 문자열을 토큰 ID로 바꾸는 과정이 필요하고, 데이터베이스에는 값의 자료형과 지켜야 할 규칙이 필요합니다. 이날 원문은 이 두 준비 과정을 각각 다룹니다.

## 1. Seq2Seq 복습에서 모델 사용으로

Seq2Seq는 입력 시퀀스를 다른 출력 시퀀스로 바꾸는 구조로, 번역이나 요약에 사용할 수 있어요. 원문의 복습 부분에는 이미지 두 장이 있지만 이미지 내용은 확인하지 않았습니다. 텍스트에 없는 구조나 설명을 이미지에서 읽은 것처럼 추가하지 않았어요. 해당 도식은 [0902 원문](https://www.notion.so/3cfeb86ebd7380c9b1cce154d3aaf771)에서 확인해야 합니다.

이후 학습 목표는 Hugging Face에서 토크나이저와 모델을 불러오고, 트랜스포머의 활용 형태를 비교하는 것입니다. 도구로는 VS Code와 Jupyter Notebook, 라이브러리로는 Transformers, PyTorch, Pandas, Matplotlib이 적혀 있어요.

Hugging Face는 모델을 공유하는 Hub와 여러 라이브러리를 포함하는 생태계입니다. 그중 `transformers`가 모델을 일관된 인터페이스로 사용할 수 있게 도와줍니다.

| 구성 요소 | 맡는 일 |
|---|---|
| `pipeline` | 작업에 맞게 전처리, 모델 추론, 후처리를 묶어 제공하는 상위 API예요. |
| `AutoTokenizer` | 모델 이름·설정에 맞는 토크나이저를 불러와요. |
| `AutoModel` 및 작업별 Auto 클래스 | 모델 설정에 맞는 구조와 가중치를 불러와요. 작업에 따라 분류·생성용 헤드가 있는 클래스를 골라야 합니다. |

> 바로잡기: 모든 `pipeline`이 반드시 같은 softmax 후처리를 하는 것은 아닙니다. 분류, 생성 등 작업에 따라 처리 방식이 달라요. `AutoModel`도 모든 작업을 자동 완성하는 클래스는 아니며, 텍스트 생성 등에는 목적에 맞는 모델 클래스가 필요합니다. Hugging Face에 공개된 모델이 모두 같은 오픈소스 라이선스를 갖는 것도 아닙니다.

원문은 인코더 전용, 디코더 전용, 인코더-디코더를 비교·구현하는 것을 학습 목표로 제시하지만, 해당 구현 코드는 이 페이지에 없습니다. 개념을 연결하기 위한 보충으로 구분하면, 인코더 전용은 입력 표현을 활용하는 분류 등에, 디코더 전용은 다음 토큰 생성에, 인코더-디코더는 입력을 조건으로 하는 번역·요약 등에 쓰입니다. 이 구분은 활용 방향이지 각 구조의 유일한 용도는 아니에요.

## 2. 토크나이저는 모델의 어휘 사전에 맞춰요

임베딩 층은 원문 문자열을 직접 받지 않습니다. 토크나이저가 텍스트를 나누고 정수 ID로 바꾸면, 임베딩 층이 그 ID에 해당하는 벡터를 찾아요. 따라서 모델과 다른 어휘 사전의 토크나이저를 임의로 섞어 쓰면 안 됩니다.

| 이름 | 이해할 내용 |
|---|---|
| BPE | 자주 함께 나타나는 인접 기호 쌍을 반복 병합해 부분 단어 어휘를 만드는 방식이에요. 바이트 기반 변형도 있습니다. |
| WordPiece | 부분 단어 어휘를 사용하는 방식이에요. 어휘 학습의 점수 기준을 단순한 쌍의 출현 빈도와 구분하며, 토큰화 단계에서는 어휘에 있는 조각으로 단어를 나눕니다. BERT가 대표 사례입니다. |
| SentencePiece | 원문 문장으로 토크나이저를 학습·사용하는 라이브러리예요. BPE나 Unigram 등의 알고리즘을 지원하며 공백도 `▁` 같은 기호로 표현할 수 있습니다. |

> 바로잡기: SentencePiece는 BPE와 서로 배타적인 단일 알고리즘이 아니에요. BPE를 SentencePiece로 학습할 수도 있습니다. 공백 표시는 일반 밑줄 `_`과 다른 `▁`가 흔히 쓰입니다. 또한 원문에서 KoBERT를 WordPiece 사례로 묶었지만, 대표적인 SKT KoBERT는 SentencePiece 기반 토크나이저를 사용합니다. Llama·Gemma 등의 토큰화 방식도 계열 이름만으로 일괄 단정하지 않고 개별 모델 설정을 확인해야 해요.

WordPiece를 설명한 ‘우도를 높여 병합한다’는 표현은 어휘 학습의 직관으로 이해하는 편이 좋습니다. 모델을 사용할 때 입력 문장마다 전체 학습 말뭉치의 우도를 다시 계산해 분할한다는 뜻은 아니에요.

## 3. 생성 설정과 과제의 재현 조건

원문에는 Gemma를 사용하며 `top_p`, `top_k`를 바꾸어 응답을 비교하라는 안내가 있습니다. 모델 성능에 대한 짧은 인상도 있지만, 평가 데이터나 결과가 없어 일반적인 성능 판단으로 옮기지는 않았어요.

- `top_k`는 다음 토큰 후보를 확률이 높은 상위 k개로 제한합니다.

이는 확률적 생성에서 후보를 고르는 설정입니다. Transformers에서 샘플링을 비교하려면 보통 `do_sample=True`가 필요하고, 모델·파이프라인이 해당 인자를 지원하는지도 확인해야 해요. 어느 설정이 항상 더 좋다는 결론은 원문에서 확인할 수 없습니다. `rtccf`라는 메모는 뜻이 풀어 쓰여 있지 않아 임의로 약어를 확장하지 않았습니다.

## 4. 데이터가 정보가 되려면 구조가 필요해요

데이터는 관측하거나 저장한 값이고, 정보는 그 값에 맥락과 의미를 부여한 것입니다. 데이터베이스는 데이터를 조직해 저장하는 대상이고, DBMS는 이를 관리하는 소프트웨어예요. SQL(Structured Query Language)은 데이터베이스의 구조를 정의하고 데이터를 조회·조작하는 언어입니다. 조회 질문만 작성하는 언어로 한정되지는 않아요.

관계형 DBMS의 예로 MySQL, Oracle Database, Microsoft SQL Server, PostgreSQL이 등장합니다. 강의는 PostgreSQL을 기준으로 진행한다고 적혀 있습니다. 이후 RAG에서 벡터 검색을 사용한다는 연결도 있지만, 이 페이지에는 벡터 검색 구현이 없습니다.

테이블은 행과 열로 값을 표현합니다. 행은 레코드, 열은 속성 또는 필드라고 부를 수 있어요. 원문의 ‘스키마’는 구조·자료형·제약의 명세라는 뜻으로 쓰였습니다. PostgreSQL에서 `schema`는 `public`처럼 테이블 등을 묶는 이름 공간도 뜻하므로 문맥을 구분해야 해요.

기본키(PK)는 각 행을 유일하게 식별하는 열 또는 열의 조합입니다. 중복과 NULL을 허용하지 않습니다. 외래키(FK)는 다른 행을 참조하는 관계를 제약으로 표현해요. 테이블 사이의 연결이 필요한 경우 사용하는 것이지, 모든 테이블이 반드시 서로 직접 연결되어야 하는 것은 아닙니다. 설계 도구로 적힌 [ERDCloud](https://www.erdcloud.com/)는 이러한 구조와 관계를 그리는 도구이며 DBMS 자체와는 역할이 달라요.

## 5. 무결성은 저장할 수 있는 값을 제한해요

회원 번호가 중복되거나 존재하지 않는 학과를 학생이 참조하면 데이터 해석이 어려워집니다. 무결성 제약은 이런 상태가 저장되는 것을 막는 규칙이에요.

| 구분 | 규칙과 수단 |
|---|---|
| 개체 무결성 | 기본키는 유일하고 NULL이 아니어야 해요. |
| 참조 무결성 | 외래키는 허용된 참조 대상에 존재해야 하며, 허용된다면 NULL일 수 있어요. |
| 도메인 무결성 | 자료형, `CHECK`, `NOT NULL` 등으로 열에 허용되는 값을 정해요. |
| 사용자 정의 무결성 | 급여가 양수여야 한다는 식의 업무 규칙을 반영해요. 단순 규칙은 `CHECK` 등으로 표현합니다. |

> 바로잡기: SQL에서 기본키 없는 테이블을 만드는 것 자체가 금지되지는 않습니다. 다만 행 식별과 관계 설계에 기본키가 유용합니다. 외래키의 참조 대상도 PK만 가능한 것은 아니며 적절한 UNIQUE 키 등이 될 수 있어요. `DEFAULT`는 값을 생략했을 때 기본값을 채우는 기능이지, 다른 값이나 명시적인 NULL을 막는 검증 제약은 아닙니다.

다음은 원문의 `Students` 예시를 SQL 코드로 올바르게 표시하고, 먼저 필요한 `Departments`를 보충한 예시입니다. 실제 데이터베이스에서 실행하지 않았습니다.

```sql
CREATE TABLE Departments (
    department_id INT PRIMARY KEY
);

CREATE TABLE Students (
    student_id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    age INT CHECK (age >= 0),
    department_id INT,
    FOREIGN KEY (department_id)
        REFERENCES Departments (department_id)
);
```

`age >= 0`은 음수를 막지만 NULL을 금지하지 않습니다. 나이를 반드시 받는 설계라면 `NOT NULL`도 필요해요. 여기서는 원문처럼 나이와 학과가 생략될 수 있는 형태를 유지했습니다.

## 6. 자료형을 쇼핑몰의 값과 연결하기

자료형은 화면에 보이는 모양보다 값의 의미를 기준으로 고르는 편이 좋습니다. 전화번호와 우편번호는 숫자로 보여도 계산할 양이 아니에요. 문자열로 저장하면 앞자리 0을 유지할 수 있습니다.

| PostgreSQL 자료형 | 쓰임과 주의점 |
|---|---|
| `SMALLINT`, `INTEGER`, `BIGINT` | 각각 2·4·8바이트 정수형이에요. 수량과 정수 식별자 등에 씁니다. |
| `REAL`, `DOUBLE PRECISION` | 각각 4·8바이트 부동소수점형이며 근삿값을 저장해요. |
| `DECIMAL(p, s)` / `NUMERIC(p, s)` | 전체 자릿수 p와 소수 자릿수 s를 정하는 정확 수치형이에요. 가격처럼 십진 정밀도가 필요한 값에 적합합니다. 정해진 소수 자리보다 정밀한 입력은 반올림될 수 있어요. |
| `CHAR(n)` | 길이 n의 고정 길이 문자형으로 공백 패딩이 적용됩니다. |
| `VARCHAR(n)` | 최대 n자라는 제약이 있는 가변 길이 문자열이에요. 저장에는 값 외의 관리 정보도 필요합니다. |
| `TEXT` | 선언 시 길이를 지정하지 않는 문자열이에요. 반드시 여러 줄 텍스트에만 쓰는 것은 아닙니다. |
| `BOOLEAN` | 참·거짓을 저장합니다. NULL은 ‘세 번째 참거짓 값’이라기보다 값이 없거나 알려지지 않은 상태예요. SQL 조건 평가에는 UNKNOWN이 나타날 수 있습니다. |
| `DATE`, `TIME` | 각각 날짜와 시간을 나타내요. |
| `TIMESTAMP` | 시간대 없는 날짜와 시간입니다. |
| `TIMESTAMPTZ` | 시간대 정보를 해석해 같은 순간을 저장하고, 조회 시 세션 시간대에 맞춰 표시합니다. 원래의 시간대 이름을 그대로 보존하는 것은 아닙니다. |
| `JSON`, `JSONB` | JSON 문서를 저장합니다. `JSONB`는 처리·인덱싱에 유용한 분해된 이진 표현을 사용하지만 모든 작업에서 무조건 빠르다는 뜻은 아니에요. |
| `ENUM` | 미리 정의한 선택지로 값을 제한하는 사용자 정의 타입이에요. |
| `vector(차원)` | pgvector 같은 확장을 설치했을 때 사용하는 벡터 타입입니다. PostgreSQL 기본 내장 타입으로 가정하면 안 됩니다. |

> 바로잡기: 원문의 `timestampz`는 `timestamptz`가 맞습니다. `TIMESTAMP`와 `TIMESTAMPTZ`는 시간대 처리 방식이 달라요. UTC는 영국의 현지 시각과 항상 같지 않고, 출력 시간대도 무조건 UTC로 고정되지 않습니다. PostgreSQL의 ENUM은 열에 바로 `enum(...)`을 쓰는 다른 DBMS 문법과 구분해야 해요.

```sql
-- 원문에 나온 상태 선택지를 PostgreSQL 문법으로 정리한 예시입니다.
CREATE TYPE order_status AS ENUM ('ready', 'order', 'delivery');
```

회원 테이블을 설계할 때는 로그인 ID, 이름, 휴대전화, 이메일, 가입 시각, 생일·배송지·우편번호 같은 값이 후보가 됩니다. 원문은 `id VARCHAR(50)`, 이름 `VARCHAR(45)`, 전화번호 `VARCHAR(15)` 같은 길이를 예로 들지만, 이는 보편적인 정답이 아니라 서비스 요구에 맞춰 정할 값입니다. 성별 등 개인정보도 필요성과 허용 범위를 먼저 정해야 해요.

비밀번호는 평문이나 복호화 가능한 단순 암호화 값으로 저장하는 예제를 만들지 않습니다. 애플리케이션에서 안전한 비밀번호 해시를 생성해 저장하거나 인증 서비스를 사용해야 해요. 원문의 `pw VARCHAR(65)`도 해시 방식마다 저장 형식이 달라 고정 규격으로 쓸 수 없습니다. 이름은 동명이인이 있어 기본키로 적합하지 않고, 별도 식별자를 두는 편이 안정적입니다. 기본키가 반드시 사용자에게 의미 있는 값일 필요는 없어요.
