# 0903 TIL | 자료형과 제약조건, 데이터베이스 정규화

회원이 여러 동아리에 가입하는 상황을 생각하면, 테이블을 만든다는 말이 단순히 열 이름을 적는 일은 아니라는 걸 알 수 있어요. 무엇으로 가입 내역을 식별할지, 어떤 값은 저장하지 못하게 할지, 회원 정보가 바뀌면 어디를 수정할지까지 정해야 합니다. 이날 노트는 자료형 복습에서 SQL 명령, 키와 제약조건, 정규화로 이어집니다.

## 1. 모델 복습과 데이터베이스 학습의 구분

원문 앞부분에는 토크나이저, `device_map="auto"`, `accelerate`, 인과적 마스킹을 복습하는 짧은 메모가 있습니다.

`device_map="auto"`는 지원되는 모델 로딩 경로에서 가중치 배치를 자동으로 정하도록 요청하는 설정이에요. Accelerate가 관련 기능을 제공하며, 장치와 메모리 조건에 따라 동작합니다. 이 문자열 하나로 모든 모델이 GPU에 올라가거나 메모리 문제가 해결되는 것은 아닙니다. 원문에는 모델 이름이나 로딩 코드가 없어 완성된 실행 예시로 늘리지 않았어요.

인과적 마스킹은 디코더가 미래 정답을 보지 못하게 합니다. 행을 현재 질의 위치, 열을 참조 위치로 둔 행렬에서는 대각선 위의 미래 위치를 차단해요. 예측을 막는 것이 아니라 다음 토큰 예측에 필요한 조건을 지키는 장치입니다.

이후에는 관계형 데이터베이스로 주제가 바뀝니다. ‘관계형’은 관계 모델을 바탕으로 데이터를 표현한다는 뜻이며, 모든 테이블이 서로 외래키로 연결되어야 한다는 뜻은 아닙니다.

## 2. 쇼핑몰의 값을 보고 자료형 고르기

원문 표에는 여러 DBMS의 타입이 섞여 있어 PostgreSQL 중심으로 구분했습니다. 값이 숫자처럼 보인다고 무조건 정수로 저장하지 않는 것이 출발점이에요. 외부 결제 거래 ID처럼 문자나 앞자리 0이 포함될 수 있는 식별자는 문자열이 더 적절할 수 있습니다.

| 값의 종류 | PostgreSQL에서 고려할 타입과 예 |
|---|---|
| 가격·세금·할인율·환불액 | `NUMERIC(p, s)` / `DECIMAL(p, s)`: 십진 정밀도가 필요한 값에 사용해요. p는 전체 자릿수, s는 소수 자릿수입니다. |
| 재고·수량·정수 식별자·리뷰 수 | `INTEGER`는 4바이트, `BIGINT`는 8바이트 정수예요. 예상 범위를 보고 정합니다. |
| 나이·별점·상태 코드 | 작은 범위라면 2바이트 `SMALLINT`를 고려하고, 별점 범위 등은 별도 `CHECK`로 제한해요. |
| 이름·이메일·전화번호·주소·쿠폰 코드 | 길이를 제한할 때 `VARCHAR(n)`를 사용합니다. 저장에는 문자열 외의 관리 정보도 들어가요. |
| 국가·통화 등 정해진 길이 코드 | `CHAR(n)`을 사용할 수 있어요. 공백 패딩 동작을 이해해야 합니다. |
| 상품 설명·약관·리뷰·문의 내용 | `TEXT`로 저장할 수 있어요. |
| 주문·결제·가입·감사 로그 시각 | 전 세계에서 같은 순간을 비교하려면 `TIMESTAMPTZ`를 고려해요. |
| 시간대 없는 날짜·시간 | `TIMESTAMP`는 지역 시각 자체를 저장할 때 사용할 수 있지만, 예약 발송처럼 실제 순간이 필요한 기능에서는 시간대도 함께 설계해야 합니다. |
| 생일·배송 예정일·행사 날짜 | `DATE`를 사용해요. |
| 활성 상태·재고 유무·수신 동의 | `BOOLEAN`을 사용하고 NULL 허용 여부도 정해요. |
| 이진 파일 데이터 | PostgreSQL에서는 보통 `BYTEA` 등을 고려합니다. 큰 이미지는 외부 저장소에 두고 안정적인 객체 경로나 URL을 저장하는 설계도 흔해요. |
| 상품 옵션·사용자 설정·웹훅 본문 | `JSON` / `JSONB`를 고려해요. 구조가 달라지는 값을 담기 편하지만 무결성과 조회 방식을 함께 설계해야 합니다. |

> 바로잡기: 원문의 `TINYINT`, `LONGTEXT`, `DATETIME`, `BLOB`, `TINYINT(1)`을 PostgreSQL 타입처럼 그대로 사용할 수는 없습니다. 특히 `TINYINT`의 범위도 DBMS와 부호 설정에 따라 달라요. `TIMESTAMP`와 `TIMESTAMPTZ`가 모두 시간대 변환을 하는 것도 아닙니다. `NUMERIC`은 십진수를 정확하게 표현하지만 지정한 s보다 많은 소수 자리는 반올림될 수 있으므로 ‘어떤 경우에도 반올림이 없다’고 설명하면 안 됩니다.

`JSONB`는 분해된 이진 표현과 인덱스를 활용할 수 있습니다. 모든 JSON 열이 자동으로 인덱스를 갖거나 모든 질의가 빨라지는 것은 아니에요. 이미지 저장 방식도 ‘반드시 외부 저장소여야 한다’는 규칙보다는 크기·접근 방식·운영 조건에 따라 선택할 설계입니다.

## 3. SQL 명령은 무엇을 바꾸는지로 구분해요

| 범주 | 명령과 역할 |
|---|---|
| DDL, 데이터 정의어 | `CREATE`, `ALTER`, `DROP`: 테이블 등 객체의 구조를 정의·변경·삭제해요. |
| DML, 데이터 조작어 | `INSERT`, `UPDATE`, `DELETE`: 행을 추가·수정·삭제합니다. `SELECT`를 포함해 설명하기도 해요. |
| DQL, 데이터 질의어 | `SELECT`를 조회 범주로 별도 분류할 때 쓰는 이름입니다. |
| DCL, 데이터 제어어 | `GRANT`, `REVOKE`: 권한을 부여·회수해요. |
| TCL, 트랜잭션 제어어 | `BEGIN`, `COMMIT`, `ROLLBACK`: 변경을 하나의 단위로 묶고 확정하거나 취소해요. |

> 바로잡기: 원문에서 TCL이 DCL 항목 아래에 섞여 있었지만, 여기서는 역할을 구분했습니다. `ALTER`는 구조를 바꾸므로 DDL이지만, 열 삭제나 타입 변경은 기존 데이터에도 영향을 줄 수 있습니다. ‘데이터에 영향이 없다’고 단정하면 안 돼요.

SQL 키워드는 대소문자를 구분하지 않는 경우가 일반적이며, 가독성을 위해 대문자로 쓰기도 합니다. 다만 PostgreSQL에서 큰따옴표로 감싼 식별자의 대소문자나 문자열 값까지 무시되는 것은 아니에요. 예시는 문장 끝에 세미콜론을 붙였습니다.

## 4. 테이블의 키와 제약조건 정하기

`CREATE TABLE 테이블명 (열이름 자료형 제약조건, ...)`으로 열을 정의합니다. 문법 안내의 대괄호는 선택 사항을 나타낼 뿐 실제 SQL에 넣는 기호는 아니에요.

| 항목 | 보장하거나 설정하는 내용 |
|---|---|
| `PRIMARY KEY` | 중복과 NULL을 허용하지 않는 대표 식별자예요. 한 테이블의 기본키는 하나지만 여러 열을 조합할 수 있어요. |
| `NOT NULL` | 값을 반드시 갖도록 합니다. |
| `UNIQUE` | 중복 값을 제한합니다. PostgreSQL 기본 동작에서는 NULL끼리는 같은 값으로 보지 않아 여러 NULL을 허용해요. |
| `CHECK` | 비교식과 `AND`, `OR`, `NOT` 등을 사용해 업무 규칙을 검사합니다. NULL 때문에 식이 UNKNOWN이면 통과할 수 있어요. |
| `DEFAULT` | 입력을 생략할 때 사용할 값이나 `CURRENT_TIMESTAMP` 같은 표현식을 정합니다. 명시적 NULL을 금지하지는 않아요. |
| `FOREIGN KEY` / `REFERENCES` | 존재하는 부모 키를 참조하도록 제한합니다. 허용되는 열이라면 NULL도 가능합니다. |

개체 무결성은 행의 식별, 참조 무결성은 부모와 자식의 연결, 도메인 무결성은 값의 범위·형식을 다룹니다. 여기에 업무별 제약이 더해집니다. SQL은 기본키 없는 테이블 생성도 허용하지만, 실무 설계에서는 행을 안정적으로 식별할 키가 필요해요. 외래키는 기본키 외에도 조건을 충족하는 UNIQUE 키 등을 참조할 수 있습니다.

자동 증가 식별자는 `INT GENERATED ALWAYS AS IDENTITY`처럼 선언할 수 있어요. PostgreSQL의 `SERIAL`, `BIGSERIAL`도 관련 편의 문법입니다. 번호를 생성하는 기능과 유일성을 강제하는 제약은 별개이므로, 식별자로 사용할 때 `PRIMARY KEY`나 `UNIQUE`를 함께 생각해야 합니다.

### 4.1 복합키로 가입 내역 표현하기

회원 한 명이 두 동아리에 가입할 수 있다면 회원 번호 하나만으로 가입 행을 식별할 수 없어요. `(user_seq, club_name)`의 조합을 기본키로 삼는 원문의 예시가 이 상황입니다.

다음은 원문의 생성·삽입·조회 순서를 정리한 예시입니다. 원문은 `DROP TABLE` 직후 그 테이블에 `INSERT`를 실행하는 순서여서, 삭제 명령을 분리했습니다.

```sql
CREATE TABLE club_members (
    user_seq INT,
    club_name VARCHAR(50),
    user_name VARCHAR(45),
    age INT CHECK (age <= 25),
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_seq, club_name)
);

INSERT INTO club_members (user_seq, club_name, user_name, age)
VALUES (1, '전자기타', '김철수', 23);

SELECT * FROM club_members;

-- 모든 사용을 마친 실습 테이블을 정말 지울 때만 별도로 실행합니다.
-- DROP TABLE club_members;
```

`CHECK (age <= 25)`는 원문의 조건을 유지한 것입니다. 0 미만 나이나 NULL까지 막지는 않아요. 나이가 필수이고 범위가 정해져 있다면 `NOT NULL`과 하한 조건을 추가해야 합니다. 이름·나이를 가입 행마다 반복 저장하는 문제는 뒤의 정규화와 연결됩니다.

### 4.2 외래키로 회원과 가입 내역 연결하기

아래는 같은 `club_members` 이름을 쓰는 **대안 설계**입니다. 위 테이블에 이어 실행하는 스크립트가 아닙니다. `members(seq)`가 존재하고 참조 가능한 키라는 전제가 있어요.

```sql
CREATE TABLE club_members (
    seq SERIAL PRIMARY KEY,
    user_seq INT REFERENCES members (seq),
    club_name VARCHAR(40),
    user_name VARCHAR(40),
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- members에 seq = 5인 행이 먼저 존재해야 합니다.
INSERT INTO club_members (user_seq, club_name)
VALUES (5, '통기타');

SELECT * FROM club_members;
```

원문의 `members` 조작 코드는 전체 스키마가 없어 독립 실행 가능한 예제로 단정할 수 없습니다. 그중 `member_pw`에 단순 비밀번호를 넣던 줄은 공개용 예제에서 제외했어요. 실제 비밀번호는 인증 서비스나 안전한 해시 처리로 관리해야 합니다. 다음 삭제 구문은 회원 식별자와 영향을 확인한 뒤 사용하는 별도 예시입니다.

```sql
-- 참조하는 자식 행이 있으면 설정된 외래키 동작에 따라 실패할 수 있습니다.
DELETE FROM members WHERE seq = 5;
```

기본 외래키 동작에서는 참조 중인 부모를 삭제하려는 작업이 제한됩니다. `ON DELETE CASCADE`를 지정하면 관련 자식 행까지 삭제하고, `ON DELETE SET NULL`은 자식 외래키를 NULL로 바꿉니다. `SET NULL`은 열이 NULL을 허용해야 합니다. 외래키가 있다고 항상 부모를 삭제할 수 없다는 말은 이 삭제 동작 옵션을 생략한 설명이에요.

## 5. DELETE, TRUNCATE, DROP을 혼동하지 않기

`INSERT INTO ... VALUES ...`는 행을 추가하고, `DELETE FROM ... WHERE ...`는 조건에 맞는 행을 삭제합니다. 삭제 범위를 확인하려면 같은 조건의 `SELECT`로 먼저 대상을 살펴볼 수 있어요.

| 명령 | 남는 것과 사라지는 것 |
|---|---|
| `DELETE FROM members WHERE seq = 5;` | 조건에 맞는 행만 삭제하고 테이블 구조는 남겨요. |
| `DELETE FROM members;` | 전체 행을 삭제하지만 구조는 남아요. |
| `TRUNCATE TABLE members;` | 테이블 전체를 비우며 구조는 유지해요. 외래키·잠금 등 동작을 확인해야 합니다. |
| `DROP TABLE club_members;` | 테이블 객체 자체를 삭제합니다. |

`TRUNCATE`가 시퀀스까지 항상 초기화하는 것은 아닙니다. PostgreSQL에서는 필요에 따라 `RESTART IDENTITY`를 지정합니다. PostgreSQL의 많은 DDL과 `TRUNCATE`는 트랜잭션 안에서 롤백할 수 있어요. 반면 이미 커밋된 변경은 다음 `ROLLBACK`으로 되돌릴 수 없습니다. 이 노트에서는 어떤 삭제 명령도 실제로 실행하지 않았습니다.

## 6. 정규화는 중복 때문에 생기는 수정 문제를 줄여요

데이터베이스 정규화는 머신러닝의 규제(regularization)와 다른 개념이며, 영어로는 normalization입니다. 같은 회원의 이름을 동아리 가입 행마다 저장하면 이름을 바꿀 때 여러 행을 고쳐야 해요. 일부만 바꾸면 서로 다른 이름이 남습니다. 정규화는 이런 중복과 삽입·수정·삭제 이상을 줄이기 위해 관계를 나누는 과정입니다.

- 제1정규형(1NF)은 관계의 속성 값이 정한 도메인에서 원자적으로 다뤄지도록 합니다. 한 칸에 여러 동아리 이름을 목록처럼 넣고 반복 그룹을 만드는 대신 가입 관계를 행으로 표현하는 것이 기본 예예요.
- 제2정규형(2NF)은 1NF를 만족하면서 후보키의 일부에만 의존하는 비주요 속성의 부분 종속을 제거합니다. 복합키가 있을 때 특히 살펴볼 부분입니다.
- 제3정규형(3NF)은 원문에 제목만 있고 설명은 비어 있습니다. 아래 설명은 이해를 잇기 위한 보충입니다.

가입 테이블의 키가 `(user_seq, club_name)`인데 `user_name`이 `user_seq`만으로 결정된다면, 이름은 복합키 전체가 아니라 일부에 의존합니다. 회원 테이블로 옮기고 가입 테이블은 회원을 참조하도록 나누는 것이 2NF를 이해하는 예예요. 단, 실제 함수 종속은 서비스 규칙으로 확인해야 합니다.

보충으로 3NF는 비키 속성을 경유한 종속을 제거하는 단계로 이해할 수 있어요. 예를 들어 회원 테이블에서 `department_id`가 `department_name`을 결정한다면 학과 정보를 별도 테이블로 나눌 수 있습니다. 엄밀하게는 모든 비자명한 함수 종속 `X → A`에 대해 X가 슈퍼키이거나 A가 후보키에 속한 속성이어야 합니다. 이 학과 예시는 원문에 있는 실습 결과가 아닙니다.
