# 0909 TIL | 트랜잭션과 Supabase SDK, LLM 입출력 구조

데이터를 한 번 수정하는 것과 애플리케이션의 작업 하나를 안전하게 끝내는 것은 다른 문제예요. 주문이나 예약처럼 여러 변경이 연결되면, 어디서 시작하고 어디서 확정할지 정해야 합니다. 이 노트는 트랜잭션의 경계를 먼저 이해하고, Python 코드가 Supabase와 연결되는 방식, LLM에 입력을 구성하는 방식으로 이어집니다.

## 1. 트랜잭션은 작업의 경계예요

트랜잭션은 하나 이상의 SQL 작업을 논리적인 실행 단위로 묶습니다. 자동 커밋 환경에서는 각 SQL 문이 개별 트랜잭션으로 처리될 수 있지만, 언제나 ‘SQL 문 하나가 곧 트랜잭션 하나’인 것은 아니에요. `BEGIN`부터 `COMMIT` 또는 `ROLLBACK`까지 여러 문장을 한 단위로 묶을 수 있습니다.

> 바로잡기: `INSERT` 뒤에 언제나 즉시 `COMMIT`이 붙는다는 설명은 자동 커밋일 때의 직관입니다. 드라이버나 도구의 설정, 명시적으로 연 트랜잭션에 따라 실제 커밋 시점이 달라집니다.

ACID는 이 단위가 가져야 할 성질을 설명해요.

| 원칙 | 뜻과 적용할 때 생각할 점 |
|---|---|
| Atomicity, 원자성 | 하나의 트랜잭션에 속한 변경을 모두 반영하거나 모두 취소합니다. 일부 변경만 남는 상태를 막아요. |
| Consistency, 일관성 | 정해진 무결성 규칙을 지키는 상태로 완료되어야 합니다. 모든 업무 규칙을 DB가 자동으로 알아서 보장하는 것은 아니므로 제약과 코드가 필요해요. |
| Isolation, 격리성 | 동시에 실행되는 트랜잭션의 상호 영향을 제어합니다. 실제로 허용되는 관찰·간섭은 격리 수준에 따라 달라집니다. |
| Durability, 지속성 | 커밋된 변경은 장애 이후에도 유지되도록 보장합니다. 이것이 백업이나 복구 계획이 불필요하다는 뜻은 아니에요. |

원문에는 공연 예매의 중복 예약이 격리성 예로 등장합니다. 트랜잭션으로 묶었다는 사실만으로 모든 중복 예약이 자동 차단되지는 않습니다. 좌석을 읽고 예약하는 쿼리 방식, 격리 수준, 잠금과 유일성 제약을 함께 설계해야 해요.

## 2. BEGIN, COMMIT, ROLLBACK으로 직접 경계 정하기

`BEGIN`은 트랜잭션을 시작하고, `COMMIT`은 변경을 확정하며, `ROLLBACK`은 아직 확정하지 않은 변경을 취소합니다. 이 명령들을 TCL(Transaction Control Language)이라고 부릅니다.

```sql
BEGIN;

-- 이 사이에 하나의 작업으로 묶을 SQL 문들을 작성합니다.

COMMIT;
```

원문의 `COMMIT:`은 문장 종료 기호를 고쳐 `COMMIT;`으로 정리했어요. 위 블록은 구조만 보여주는 틀로 실제 업무 처리가 들어 있지는 않습니다.

다음은 원문의 `users` 삭제 후 롤백 예시입니다. 대상 테이블은 그대로 유지하되, 이메일 값은 공개용 예시 주소로 바꾸었습니다. `users(email)`이 존재한다는 전제이며 실제로 실행하지 않았어요.

```sql
BEGIN;

DELETE FROM users
WHERE email = 'example-user@example.com';

ROLLBACK;

SELECT * FROM users;
```

삭제를 확정하기 전에 롤백하므로 이 트랜잭션의 삭제 변경을 취소하는 흐름입니다. 실제로 어떤 행이 있었는지, 삭제 대상이 몇 건인지 확인한 결과는 아닙니다. 이메일이 유일하다는 제약이 없다면 여러 행이 대상이 될 수도 있어요.

> 바로잡기: `ROLLBACK`은 과거의 모든 데이터 상태를 자유롭게 복원하는 명령이 아닙니다. 이미 커밋한 변경을 나중의 롤백으로 취소할 수는 없어요. 커밋 후 복구에는 반대 작업을 하는 새 트랜잭션, 백업 복원 등 별도의 방법이 필요합니다.

## 3. FOR UPDATE 잠금은 트랜잭션 끝까지 생각해요

원문에는 `SELECT ... FOR UPDATE`와 ‘수정작업이 끝나야 잠금이 풀린다’는 설명이 있습니다. PostgreSQL에서 이 구문은 조회한 행에 잠금을 걸어, 다른 트랜잭션의 충돌하는 수정이나 행 잠금 획득을 기다리게 할 수 있어요.

> 바로잡기: 행 잠금은 일반적으로 `UPDATE` 한 문장이 끝났을 때가 아니라 해당 트랜잭션이 `COMMIT` 또는 `ROLLBACK`으로 끝날 때 해제됩니다. 일반적인 읽기까지 모두 막는 것도 아닙니다.

예약 예에서는 좌석 상태를 잠금과 함께 읽고, 같은 트랜잭션 안에서 예약 가능 여부를 확인한 뒤 갱신해야 합니다. 이 노트에는 좌석 테이블 스키마가 없으므로 임의의 실습 쿼리를 완성하지 않았어요. 경합이 많으면 대기나 교착 상태에 대한 처리도 필요하므로 잠금을 걸기만 하면 모든 문제가 해결되는 것은 아닙니다.

## 4. 데이터베이스, API, SDK는 맡는 일이 달라요

Supabase의 데이터베이스는 데이터를 저장하고 제약을 적용합니다. API는 애플리케이션이 기능을 요청하는 인터페이스이고, SDK(Software Development Kit)는 Python 같은 언어에서 그 인터페이스를 편하게 호출하도록 돕는 도구 모음이에요.

설계할 때의 흐름과 실제 요청이 흐르는 길을 구분하면 용어가 덜 섞입니다.

```text
설계: 저장할 데이터와 관계 정의 → 테이블·제약조건 설계
실행: Python 애플리케이션 → Supabase SDK → API → 데이터베이스
```

이는 원문의 ‘database, api, sdk 구조’를 연결하는 보충 설명입니다. Table Editor나 SQL Editor는 관리 도구이지, 모든 애플리케이션 요청이 반드시 거쳐 가는 중간 단계는 아니에요.

### 4.1 환경 변수에서 클라이언트 설정 읽기

원문의 클라이언트 생성 코드는 SQL로 표시되어 있었지만 실제로는 Python입니다. 아래는 블록 언어와 환경 변수 오타를 고치고, 값이 없을 때 명확히 실패하도록 점검을 추가한 예시예요.

```python
import os
from supabase import create_client

url = os.getenv("SUPABASE_URL")
key = os.getenv("SUPABASE_PUBLISHABLE_KEY")

if not url or not key:
    raise RuntimeError(
        "SUPABASE_URL과 SUPABASE_PUBLISHABLE_KEY를 환경 변수에 설정해 주세요."
    )

supabase = create_client(url, key)
```

> 코드 수정: 원문의 `SUPBABASE_URL`은 `SUPABASE_URL`로 고쳤습니다. 이 이름을 바꾸어 사용하는 예제라는 뜻이며, 실제 로컬 환경 변수를 조회하거나 변경하지 않았습니다. 원문의 `SUPABASE_PUBLISHABLE_KEY`는 그대로 유지했어요.

`os.getenv()`는 프로세스의 환경 변수를 읽습니다. `.env` 파일을 자동으로 읽는 함수는 아니므로 별도의 로더나 실행 환경 설정이 필요할 수 있어요. 위 예제는 `supabase` Python 패키지와 환경 변수 설정이 준비되어 있다는 전제입니다.

클라이언트를 만들었다고 로그인이나 데이터 조회가 완료되는 것은 아닙니다. 프로젝트 URL과 공개 클라이언트용 키는 프로젝트 API 설정이고, 개별 사용자의 인증 세션과는 달라요. 네트워크 요청을 성공시켰는지도 별도로 확인해야 합니다. 이 변환 작업에서는 코드를 실행해 환경 변수를 읽지 않았고, 클라이언트 생성·네트워크 연결도 시도하지 않았습니다.

### 4.2 인증과 데이터 권한은 아직 구현되지 않았어요

원문의 `authentication` 탭은 제목 외에 내용이 없습니다. 따라서 가입·로그인이나 CRUD 구현을 실제 강의 코드처럼 추가하지 않았어요.

경계를 이해하기 위한 보충으로, 인증은 요청자가 누구인지 확인하고 인가는 그 사람이 어떤 행에 접근할 수 있는지 정합니다. 프로젝트 키만 넣는 것과 로그인은 다르며, 클라이언트의 조회 필터만으로 권한을 보장할 수도 없습니다. 사용자별 데이터는 적용되는 권한과 RLS(Row Level Security) 같은 데이터베이스 정책으로 보호해야 합니다. 구체적인 정책은 이 원문에 없으므로 검증된 정책 코드로 제공하지 않습니다.

또 앞의 SQL 예제가 대상으로 삼은 `users`는 원문에 적힌 애플리케이션 테이블 이름입니다. 그것이 Supabase Auth의 `auth.users`와 같은 테이블이라고 확인된 것은 아니에요. 일반 프로필 행 삭제를 인증 계정 삭제와 동일하게 이해하면 안 됩니다.

## 5. LLM 입출력은 메시지의 역할부터 구분해요

기존 애플리케이션은 조건과 처리 규칙을 코드로 명시합니다. LLM 애플리케이션에서도 코드가 필요하지만, 모델에 보낼 메시지와 받아 온 응답을 다루는 부분이 더해져요. 이날 메모에는 LangChain, 추상화, LCEL, 시스템 메시지와 사용자 질의가 등장합니다.

LangChain은 모델 호출과 주변 구성 요소를 연결하는 프레임워크입니다. 추상화는 ‘정해지지 않은 것’이라기보다, 구현별 차이를 감추고 공통 인터페이스로 다룰 수 있게 하는 방식이에요. 모델 공급자마다 다른 호출 절차를 공통적인 방식으로 다루는 것이 한 예입니다.

LCEL(LangChain Expression Language)은 실행 가능한 구성 요소를 조합해 처리 흐름을 표현하는 방식입니다. 프롬프트 구성, 모델 호출, 응답 가공 같은 단계를 읽기 쉽게 연결할 수 있어요. 원문에는 실제 체인 코드나 파서 구현이 없으므로 특정 API 호출을 실행한 예시로 만들지 않았습니다.

| 메시지 역할 | 담을 내용 |
|---|---|
| 시스템 메시지 | 애플리케이션이 정한 역할, 응답 기준, 제약 등을 전달할 수 있어요. |
| 사용자 메시지 | 사용자가 이번에 묻는 질문이나 요청을 담습니다. |

원문은 역할·상황·제한조건·예시를 모두 시스템 요구사항으로 묶습니다. 이런 내용을 시스템 메시지에 담을 수는 있지만, 모든 상황 설명이나 예시가 반드시 시스템 메시지여야 하는 것은 아니에요. 대화 예시는 사용자·어시스턴트 메시지 쌍으로도 표현할 수 있고, API마다 지원하는 역할이 다를 수 있습니다.

특히 사용자가 보낸 텍스트나 외부 문서가 시스템 지시와 같은 권한을 갖는 것은 아닙니다. 보충 설명으로, 앱이 정한 규칙과 모델이 참고할 데이터를 분리해 전달하는 습관이 필요해요. 이 페이지의 ‘입력과 출력 구조’ 제목과 달리 출력 파서·응답 스키마의 구체 내용은 원문에 없으므로 미학습 내용을 완료한 것처럼 채우지 않았습니다.
