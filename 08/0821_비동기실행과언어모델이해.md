# 0821 TIL: 비동기의 실행 흐름과 언어 모델의 생성 방식

## 1. 기다리는 작업과 계산하는 작업을 나누기

비동기를 이해할 때는 “동시에 실행한다”보다 “기다리는 동안 누가 실행할 수 있는가”를 먼저 생각하면 좋아요. 동기 함수 호출은 결과가 돌아온 뒤 다음 줄로 진행합니다. 비동기 코루틴은 필요한 지점에서 실행을 잠시 멈추고, 이벤트 루프가 다른 준비된 작업을 진행하도록 할 수 있어요.

CPU-bound 작업은 계산 자원이 병목이고, I/O-bound 작업은 네트워크나 저장 장치의 응답을 기다리는 시간이 병목입니다. 내비게이션 클라이언트가 경로 응답을 기다리는 부분은 I/O의 예지만, 서버가 경로를 계산하는 부분에는 CPU 작업도 있어요. 한 서비스 안에도 두 종류의 작업이 섞일 수 있습니다.

> 정정: CPU 작업은 무조건 동기, I/O 작업은 무조건 비동기인 것은 아니에요. 비동기는 I/O 대기를 겹치는 데 유용한 선택지이고, 무거운 CPU 계산을 저절로 여러 코어에서 실행하지 않습니다. 원문의 `serve-routine`은 `subroutine`을 의도한 것으로 보이며, 비동기 함수의 문법은 `async def 함수명():`입니다.

이벤트 루프는 준비된 작업을 실행하고, 대기하던 작업이 다시 진행할 수 있을 때 실행 기회를 주는 역할을 합니다. `await`가 항상 즉시 다른 작업으로 전환한다는 설명도 단순화예요. 기다리는 대상이 이미 완료되었다면 전환 없이 이어질 수 있습니다. 코루틴이 중간에 양보하지 않고 오래 계산하면 다른 작업도 기다리게 돼요.

## 2. 코루틴을 실행하고 결과를 모으기

일반 Python 스크립트에서는 `asyncio.run(main())`이 이벤트 루프의 생성과 실행, 종료 정리를 맡습니다. 실행 중인 이벤트 루프가 있는 노트북에서는 그 안에서 `await main()`을 사용하는 방식이 일반적이에요. 같은 스레드에서 이미 실행 중인 루프 안에 `asyncio.run()`을 중첩하면 안 됩니다.

아래는 원문에서 생략된 `work()`와 import를 채운 설명용 스크립트예요.

```python
import asyncio


async def work(title, seconds):
    await asyncio.sleep(seconds)
    return f"{title} 완료"


async def main():
    results = await asyncio.gather(
        work("작업1", 2),
        work("작업2", 3),
        work("작업3", 1),
    )
    print(results)


if __name__ == "__main__":
    asyncio.run(main())
```

`gather()`는 여러 awaitable을 함께 진행하고, 정상 완료하면 전달한 순서에 맞춰 결과 리스트를 반환합니다. 작업이 끝나는 순서와 결과 리스트의 순서는 달라질 수 있어요. 원문의 `asyncio.run(함수)`는 실행할 코루틴 객체를 넘기는 `asyncio.run(main())` 형태로 구체화했습니다.

> 정정: “마지막 작업까지 기다렸다가 항상 모든 결과를 반환한다”는 설명은 성공하는 경우에 해당해요. 기본 `gather()`는 작업에서 예외가 발생하면 첫 예외를 대기하는 호출자에게 전파합니다. 다른 작업을 자동으로 모두 취소하는 것도 아니므로 실패와 취소 정책은 따로 설계해야 해요.

## 3. HTTP 요청의 대기를 겹치기

반복문 안에서 매번 `await get_post(i)`를 하면 비동기 함수라도 요청을 하나씩 기다립니다. 반면 여러 코루틴을 모아 `gather(*get_posts)`에 전달하면 요청 대기를 겹칠 수 있어요. 여기서 `*`는 리스트의 원소를 개별 인자로 펼칩니다.

원문 HTTPX 예제는 요청마다 클라이언트를 생성했는데, 아래에서는 하나를 공유하도록 정리했어요. 연결 풀을 재사용할 수 있고 종료 시점도 한곳에서 관리할 수 있습니다. 상태 코드 검사와 타임아웃을 추가했습니다.

```python
import asyncio
import httpx


async def get_post(client, num):
    url = f"https://jsonplaceholder.typicode.com/posts/{num}"
    response = await client.get(url)
    response.raise_for_status()
    result = response.json()
    return result["id"], result["title"]


async def main():
    async with httpx.AsyncClient(timeout=10.0) as client:
        get_posts = [get_post(client, i) for i in range(1, 11)]
        results = await asyncio.gather(*get_posts, return_exceptions=True)
        for result in results:
            if isinstance(result, Exception):
                print("요청 처리 실패:", type(result).__name__)
            else:
                print(result)


if __name__ == "__main__":
    asyncio.run(main())
```

여기서는 독립적인 요청 하나의 실패가 다른 결과 확인을 막지 않도록 `return_exceptions=True`를 명시했어요. 예외도 결과 항목으로 반환하므로 반드시 구별해 처리합니다. 원문의 기본 `gather()`와 다른 실패 정책을 선택한 것입니다. 이 코드는 외부 패키지와 네트워크가 필요한 설명용 예제이며, 설치·접속·실행하지 않았습니다. 실제 서비스에는 재시도, 요청량 제한, 응답 스키마 검증 등 추가 설계가 필요해요.

`with`는 `__enter__`와 `__exit__`를 호출하고, `async with`는 비동기 컨텍스트 매니저의 `__aenter__`와 `__aexit__`를 기다립니다. `httpx.Client()`와 `httpx.AsyncClient()`의 자원 정리 방식도 이 구분에 연결돼요.

## 4. 언어 모델은 토큰을 이어서 문장을 만들어요

이날의 AI 리터러시 내용은 프로그램을 실행하는 흐름에서, 모델이 답변을 생성하는 흐름으로 관심을 옮깁니다. 자연스럽게 말한다고 사람이 가진 경험이나 의도를 그대로 갖는 것은 아니에요. 답변을 읽을 때 문장의 자연스러움과 사실의 정확성을 따로 확인해야 합니다.

LLM은 대규모 언어 모델을 뜻합니다. 생성형 자기회귀 언어 모델은 주어진 문맥을 바탕으로 다음 토큰의 확률 분포를 계산하고, 선택한 토큰을 문맥에 이어 붙이며 출력을 만듭니다. 학습에서는 데이터의 패턴을 모델 매개변수에 반영해요.

토큰은 토크나이저가 텍스트를 나누어 처리하는 단위입니다. 단어 전체일 수도 있고 단어 일부, 공백이나 기호 조각일 수도 있어요.

> 정정: 영어 한 단어가 항상 한 토큰인 것도, 한국어 토큰이 반드시 형태소 기준인 것도 아닙니다. 분할 방식과 비용은 모델·토크나이저에 따라 달라져요. “영어로 쓰면 언제나 토큰을 절약한다”는 규칙으로 일반화할 수 없습니다. 학습 데이터를 전혀 기억하지 않는다는 설명도 강한 단정이며, 일부 내용을 암기하거나 재현할 수 있습니다.

Transformer 기반 생성 흐름은 다음처럼 연결할 수 있어요.

1. 토크나이저가 텍스트를 토큰 ID로 바꿉니다.
2. 임베딩과 위치 정보가 토큰을 계산 가능한 벡터로 표현합니다.
3. Transformer 층의 self-attention과 피드포워드 네트워크가 문맥을 반영한 표현을 만듭니다.
4. 출력 점수인 logits에서 softmax 등으로 다음 토큰의 확률 분포를 얻습니다.
5. 디코딩 규칙에 따라 토큰을 선택하고 생성을 이어갑니다.

Self-attention은 토큰이 문맥의 다른 토큰과 어떻게 관련되는지를 계산해 표현을 조정합니다. 생성용 causal attention에서는 미래 위치를 보지 못하도록 마스크를 적용해요. 학습 중 여러 위치의 계산을 병렬화할 수 있다는 것과 생성 시 다음 토큰을 순차적으로 만든다는 것은 함께 성립합니다. 층 수는 모델마다 다르며, 피드포워드 층만이 사실을 저장하는 독립된 저장소인 것도 아니에요.

## 5. 임베딩 유사도와 토큰 생성은 구별해요

임베딩은 텍스트 등을 실수 벡터로 표현해 검색이나 비교에 활용하게 해 줍니다. 원문의 유클리드 거리와 코사인 유사도는 이 벡터를 비교하는 방법이에요.

| 방법 | 의미와 주의점 |
| --- | --- |
| 유클리드 거리 | 두 벡터 사이의 직선 거리이며 0 이상입니다. 값이 작을수록 가까워요. 크기와 스케일의 영향을 받습니다. |
| 코사인 유사도 | 0이 아닌 두 벡터의 방향을 비교하며 -1부터 1 사이의 값을 가집니다. 크기 자체보다 각도에 집중해요. |

코사인 유사도 0은 수학적으로 직교, -1은 반대 방향을 뜻하지만, 텍스트가 반드시 무관하거나 반의어 관계라는 뜻은 아닙니다. 임베딩 모델이 학습한 공간의 특성을 함께 봐야 해요. 영벡터에서는 일반적인 코사인 유사도 정의를 그대로 적용할 수 없습니다.

> 정정: LLM이 가장 가까운 임베딩 단어를 검색해 그대로 답을 이어 붙이는 것은 아닙니다. 임베딩은 모델의 입력 표현과 검색에 쓰일 수 있고, 다음 토큰은 문맥을 처리한 신경망의 출력 분포에서 선택합니다. 역할 프롬프트도 “그 직업 집단에 속한 토큰만 검색한다”는 원리로 설명하면 부정확해요.

## 6. 생성의 다양성을 조절하는 설정

| 설정 | 조절하는 것 |
| --- | --- |
| `top_k` | 확률이 높은 상위 K개 토큰으로 후보를 제한해요. |
| `top_p` | 확률이 높은 순서로 누적했을 때 P 이상이 되는 후보 집합을 사용해요. |
| `temperature` | 일반적으로 logits를 온도로 나누어 분포의 뾰족함을 조절해요. |

원문의 후보 `mat`, `rug`, `floor`, `couch`, `banana`는 후보 제한을 설명하기 위한 예시예요. 상위 후보를 남긴 뒤에는 남은 확률을 다시 정규화해 선택할 수 있습니다. 표에 등장한 확률들은 전체 어휘 분포를 다 적은 것이 아니므로 완전한 확률표로 옮기지 않았어요.

보통 온도가 낮아지면 높은 점수의 후보에 선택이 집중되고, 높아지면 분포가 더 평평해집니다. `temperature=1`은 그 단계에서 원래 logits의 스케일을 유지하는 기준이에요. 0은 수식에 직접 대입하기보다 API가 탐욕적 선택 등으로 별도 처리하는 경우가 있습니다.

> 정정: `top_k` 다음에 `top_p`, 마지막에 온도를 적용한다는 고정 순서는 모든 구현의 규칙이 아닙니다. 지원 여부와 적용 순서를 사용하는 API에서 확인해야 해요. 낮은 온도나 `top_k=1`도 사실성, 문법 정확성, 완전한 재현성을 보장하지 않습니다.

원문의 작업별 추천값은 보편적인 정답표로 쓰기 어렵습니다. 코드·데이터 추출에서는 출력 형식과 검증을 우선하고, 수학·논리에서는 계산과 근거를 별도로 확인해야 해요. 요약·번역은 원문 충실도를 점검하고, 대화·이메일은 표현의 적합성을 봅니다. 아이디어 발상과 창작은 다양성을 더 허용할 수 있지만, 수치 설정은 모델에 맞춰 평가해야 합니다. 이런 의도만 남기고 검증되지 않은 고정 추천 수치와 “오류 방지” 보장은 제외했어요.

## 7. 환각을 줄이려면 문맥과 검증을 함께 다뤄요

모델은 그럴듯한 문장을 생성할 수 있지만, 그 내용이 사실인지 항상 보장하지는 못합니다. 정보가 부족하거나 드문 주제에서는 불확실한 내용을 단정할 수 있어요. 환각은 단순히 “사고하지 않기 때문”이라는 한 문장으로 설명하기보다, 학습 자료·학습 목표·문맥 부족·생성 과정과 검증의 한계를 함께 보는 편이 정확합니다.

프롬프트 엔지니어링은 지시와 예시를 설계하는 일이고, 컨텍스트 엔지니어링은 필요한 자료, 대화 기록, 검색 결과 등을 선택하고 배치하는 더 넓은 작업입니다. 검색으로 찾은 근거를 넣으면 도움이 될 수 있지만 검색 결과 자체가 틀리거나 모델이 잘못 해석할 수 있으므로 환각을 완전히 없애지는 못해요.

컨텍스트 윈도우는 모델이 한 번에 다룰 수 있는 토큰 범위와 관련됩니다. 사용자 프롬프트만의 길이가 아니라 시스템 지시, 대화, 도구 결과와 출력 예산 등이 함께 관계해요. 문맥에서 이전 대화가 빠지는 것은 모델이 이미 학습한 매개변수의 지식을 지우는 현상과 다릅니다.

| 한계 | 대응할 때 생각할 점 |
| --- | --- |
| 환각 | 주장과 출처를 나누고, 근거가 없는 답을 확정 사실로 쓰지 않아요. |
| 데이터 편향 | 학습 자료와 설계·평가의 편향이 출력에 영향을 줄 수 있어요. 대표성이나 채용 판단 같은 상황에서는 차별 위험을 점검해야 합니다. |
| 지식 컷오프 | 사전 학습만으로 이후 사건을 알 수는 없어요. 검색·도구·후속 업데이트의 유무를 구별합니다. |
| 문맥 한계 | 필요한 자료를 우선하고, few-shot 예시와 RTCCF 같은 구조로 요구를 명확히 해요. |

원문의 특정 인물 이미지와 채용 사례는 별도 근거가 제공되지 않아 확인된 사건처럼 서술하지 않고 편향 위험의 예시로 정리했습니다. `human-in-the-loop`는 사람이 승인이나 판단 과정에 직접 참여하는 방식이고, `human-on-the-loop`는 주로 감독하면서 필요할 때 개입하는 방식입니다. 감독만 한다고 책임이 없어지는 것은 아니에요.

원문에 적힌 STFI는 “멈추기 → 출처 확인 → 교차 검증 → 원본 맥락 추적”이라는 확인 순서로 남깁니다. 검색 도구가 반환한 요약을 최종 출처로 삼지 말고 원자료까지 확인하는 것이 이 흐름의 목적이에요. 약어의 표준 명칭 여부와 원문의 `Atani`가 무엇을 뜻하는지는 확인되지 않았습니다.
