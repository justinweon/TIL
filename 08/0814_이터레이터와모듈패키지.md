# 0814 이터레이터와 제너레이터, 모듈과 패키지

`map()`과 `filter()`에 함수를 전달하는 방법을 익혔다면, 이제 그 함수가 데이터를 어떻게 하나씩 받는지 살펴볼 차례예요. 반복 가능한 대상과 다음 값을 꺼내는 객체를 구분하면 제너레이터의 지연 계산이 자연스럽게 이어집니다. 뒤에서는 재사용할 함수를 파일과 패키지로 나누는 방법을 정리해요.

## 1. 이름의 범위와 변환·선별 복습

LEGB는 현재 함수의 지역 범위, 바깥 함수 범위, 모듈 전역 범위, 내장 이름 공간 순으로 이름을 찾는 규칙이에요. 원문의 `Global: 전역함수`는 전역 이름 공간으로 고쳐 읽어야 합니다.

```python
counter = 0

def increase():
    global counter
    counter += 1

def local_increase():
    counter = 100

increase()
increase()
local_increase()
```

`increase()`는 전역 `counter`를 갱신하지만, `local_increase()`는 같은 이름의 지역변수를 만들어요. 따라서 마지막 함수의 대입은 전역 값에 영향을 주지 않습니다. 위 코드 자체에는 출력문이 없어요.

```python
numbers = [1, 2, 3, 4, 5]
result = list(filter(lambda x: x % 2 == 0, map(lambda x: x + 1, numbers)))
```

안쪽 `map()`은 요소에 1을 더하고, 바깥 `filter()`는 그 결과에서 짝수만 남겨요. `numbers`는 함수에 전달하는 데이터이며 쉼표는 함수 호출의 인수들을 구분합니다. 원문의 “시퀀스 구조 때문에 쉼표로 구분한다”는 설명은 수정이 필요해요. `map(function, iterable)`과 `filter(function, iterable)`은 시퀀스뿐 아니라 이터러블을 받습니다. `map()`은 여러 이터러블도 받을 수 있어요.

또한 중간 리스트 전체를 먼저 만드는 것은 아니에요. 소비할 때 각 요소가 변환·선별되는 흐름이며, 마지막 `list()`가 결과를 모읍니다. 클로저는 외부 함수가 내부 함수를 기억하는 것이 아니라, 내부 함수가 사용하는 외부 범위의 바인딩을 유지하는 구조예요.

## 2. 이터러블에서 이터레이터 얻기

이터러블(iterable)은 반복해서 요소를 얻을 수 있는 객체이고, 이터레이터(iterator)는 다음 요소를 제공하면서 순회 상태를 관리하는 객체예요. 리스트 자체와 리스트를 순회하는 객체는 역할이 다릅니다.

```python
nums = [10, 20, 30]
iter_method = nums.__iter__

for num in nums:
    print(num)

fruits = ["apple", "orange", "melon", "banana"]
it = iter(fruits)
first = next(it)
second = next(it)
```

`nums.__iter__`는 메서드를 참조하는 표현이고, `iter(nums)`는 이터레이터를 얻는 호출이에요. 이터레이터의 `__next__()`에 대응하는 `next(it)`를 호출하면 다음 값을 받습니다. 더는 값이 없으면 `StopIteration`이 발생해요. `for`는 이 종료 신호를 처리하며 반복을 끝냅니다. 튜플이나 집합을 순회할 때도 같은 프로토콜을 이용해요.

> 바로잡기: 리스트에 직접 `next(nums)`를 호출할 수는 없어요. 먼저 `iter(nums)`로 이터레이터를 얻어야 합니다. `__next__()`가 반드시 숫자 인덱스를 한 칸 이동시키는 것도 아니에요. 입력 스트림 등 인덱스 없는 대상에도 적용됩니다.

일반적으로 `__iter__()`가 이터레이터를 반환하면 반복 가능한 객체로 사용할 수 있어요. 다만 반복 가능성을 `__iter__`의 존재만으로 완전히 판단할 수는 없습니다. 파이썬은 일부 객체에 대해 정수 인덱스를 받는 `__getitem__()` 기반 순회도 지원해요. 이터레이터 자체는 `iter(it)`가 자기 자신을 반환하고 `next(it)`로 다음 값을 제공합니다.

## 3. `yield`로 필요한 값만 제공하기

제너레이터 함수는 본문에 `yield`가 있는 함수예요. 호출하면 본문을 끝까지 실행하는 대신 제너레이터 객체를 반환합니다. 다음 값을 요청할 때 실행을 진행하고, `yield`에서 값을 전달한 뒤 상태를 보존하며 멈춰요.

```python
def generate_nums():
    yield 10
    yield 20
    yield 30

gen = generate_nums()
first = next(gen)
second = next(gen)
third = next(gen)
```

이후 다시 `next(gen)`을 호출하면 제공할 값이 없어 `StopIteration`이 발생합니다. 한 번 소비한 제너레이터는 자동으로 처음부터 시작하지 않아요. 다시 순회하려면 새 객체를 만들어야 합니다.

리스트는 요소를 미리 모아 보관하지만, 제너레이터는 요청에 따라 다음 계산을 진행할 수 있어요. 큰 파일을 한 부분씩 읽거나 많은 값을 차례로 처리할 때 전체 결과를 한 번에 저장하지 않아도 된다는 장점이 있습니다.

> 바로잡기: 원문의 “`next()` 전에는 아무 데이터도 없다”는 표현은 과해요. 제너레이터도 코드·인수·지역 상태 등을 유지하고, 입력 데이터가 이미 메모리에 있을 수도 있습니다. 메모리 절약 여부는 생성 방식과 소비 방식에 달려 있어요. `list(gen)`으로 전부 모으면 결과 전체를 저장하게 됩니다.

원문의 카페 대기열·주문 제작 비유는 “요청할 때 다음 일을 진행한다”는 부분에 도움이 됩니다. 다만 제너레이터의 목적을 힙 관리 하나로 한정하거나, 무조건 실행 시간이 줄어든다고 보지는 않아야 해요.

## 4. 제너레이터 표현식과 순회 상태

리스트 컴프리헨션은 새 리스트 전체를 만들어요. 비슷한 형식을 소괄호로 쓰면 다음 값을 순차적으로 만드는 제너레이터 표현식이 됩니다.

```python
gen = (i for i in range(1, 101) if i % 2 == 0)
first = next(gen)
second = next(gen)

for num in gen:
    print(num)
```

> 바로잡기: 원문에서 빠진 `for`를 보완했습니다. 소괄호를 썼다고 튜플이 되는 것이 아니라, 이 문법은 제너레이터 표현식이에요. “튜플로 리스트 컴프리헨션을 감싼다”는 설명과 구분해야 합니다.

앞의 두 `next()`가 먼저 값을 소비했으므로 `for`는 남은 지점부터 이어집니다. 원문은 이런 호출 순서에서 반복이 6부터 시작하는 현상을 기록했어요. 이 문서에서 새로 실행한 출력이 아니라 원문이 관찰한 순회 상태를 설명한 것입니다.

## 5. 동기·비동기와 제너레이터는 다른 구분이에요

원문은 한 웨이터가 주문을 주방에 전달하고, 음식이 준비되는 동안 다른 테이블의 주문을 받는 상황으로 비동기를 설명합니다. 기다리는 동안 다른 작업을 진행할 수 있다는 점에 초점을 맞추면 좋아요.

동기 호출은 호출한 작업의 완료와 다음 진행이 연결되는 방식으로 볼 수 있습니다. 비동기 작업은 완료를 기다리는 동안 다른 작업을 진행하도록 구성할 수 있어요. 완료 순서가 시작 순서와 다를 수 있지만, 반드시 시작 순서대로 시작하거나 완료 순서대로 결과를 표시해야 한다는 규칙은 없습니다. 결과를 모으는 API와 스케줄링에 따라 달라져요.

> 바로잡기: 일반적인 `yield`와 `next()`만으로 비동기 I/O가 되는 것은 아닙니다. 위 제너레이터는 호출자가 `next()`를 부르는 동안 동기적으로 실행돼요. 비동기 처리는 `async`·`await`, 이벤트 루프 같은 별도 개념과 연결해야 합니다. 비동기가 여러 CPU 작업을 자동으로 병렬 실행하거나 항상 더 빠르게 만드는 것도 아니에요.

## 6. 재사용할 코드를 모듈에 모으기

입력과 처리 로직을 함수로 분리했다면, 여러 파일에서 쓰는 함수는 모듈로 나눌 수 있어요. 일반적인 파이썬 소스 모듈은 `.py` 파일 하나에 대응하며, 변수·함수·클래스 등을 정의합니다. 모든 모듈이 `.py` 파일인 것은 아니고 내장·확장 모듈도 있어요.

다음은 원문 `mod1.py`를 정리한 파일 구성 예시입니다. 실제 파일을 생성하거나 import 실행을 검증한 것은 아니에요.

```python
# mod1.py
def add(num1, num2):
    return num1 + num2

def minus(num1, num2):
    return num1 - num2

VERSION = "1.0.0"

if __name__ == "__main__":
    result = add(10, 20)
    print("결과:", result)
```

`VERSION`의 대문자는 상수처럼 취급하자는 관례이지 재대입을 막는 장치는 아닙니다. `"1.0.0"`은 소수점 두 개가 있는 수가 아니라 버전 문자열이므로 따옴표를 사용해요.

아래는 위 파일을 찾을 수 있는 다른 모듈에서 사용할 예시입니다. 각각의 import 방식은 대안으로 비교하면 됩니다.

```python
import mod1
result = mod1.add(10, 20)

from mod1 import add, minus, VERSION
result = add(10, 20)

import mod1 as m
result = m.add(10, 20)
```

`import mod1`은 모듈 이름으로 접근하고, `from mod1 import add`는 필요한 이름을 현재 범위에 연결해요. `as`는 별칭을 지정합니다. 무엇을 어디서 가져왔는지 보여주는 이름을 유지하면 코드 읽기가 쉬워져요.

### 모듈 이름과 직접 실행 구분

`__name__`은 보통 import된 모듈의 이름이고, 직접 실행한 최상위 모듈에서는 `"__main__"`입니다. 패키지 안에서는 `package.module`처럼 전체 모듈 이름이 될 수 있으므로 파일명만이라고 단정하지 않아야 해요.

모듈의 최상위 코드는 처음 import할 때 실행될 수 있습니다. 원문의 `print("모듈명:", __name__)`와 덧셈 출력이 import만 해도 나타난 이유가 여기에 있어요. 위 예제의 `if __name__ == "__main__":`은 직접 실행할 때만 예제 계산을 하도록 보완한 부분입니다.

> 바로잡기: import할 때마다 캐시를 지워야 하는 것은 아니에요. 같은 프로세스에서는 보통 `sys.modules`에 이미 불러온 모듈을 재사용합니다. 소스를 수정한 노트북에서는 커널 재시작이나 필요에 따른 `importlib.reload()`를 검토할 수 있지만, `__pycache__` 삭제와 모듈 재로딩은 다른 문제예요. `reload()`도 기존 객체 참조를 모두 새것으로 바꾸지는 않습니다.

## 7. 패키지, 초기화와 상대 import

패키지는 관련 모듈을 묶는 구조예요. 일반 패키지는 디렉터리에 `__init__.py`를 두며, 그 파일에서 초기화 코드나 공통 이름을 정의할 수 있습니다. 보통 최초 import 때 실행되고 같은 프로세스에서 매번 반복되지는 않아요.

다음은 원문의 `game` 예시를 정리한 것입니다. `game/lol.py`와 `game/wow.py`의 구현은 제공되지 않았으므로 패키지 구조를 설명하는 불완전한 파일 예시예요.

```python
# game/__init__.py
from . import lol

print("공통 초기화 작업을 수행합니다.")

def common_function():
    return "공통 기능"

COMMON_VAR = "공통 변수"
__all__ = ["lol"]
```

```python
# 위 game 패키지가 실제로 존재해야 해요.
import game
result = game.common_function()

from game import *
```

`__all__`은 와일드카드 import로 내보낼 이름을 정해요. 여기서는 `lol`을 공개하도록 지정했지만 `game.common_function()`처럼 명시적으로 접근하는 것까지 막지는 않습니다. `__all__`에는 모듈뿐 아니라 함수·변수 등의 이름도 들어갈 수 있어요. 원문의 `import lol`은 형제 모듈을 뜻하도록 `from . import lol`로 고쳤습니다.

> 바로잡기: 파이썬 3.3 이후 `__init__.py` 없는 네임스페이스 패키지를 지원하지만, 모든 폴더가 무조건 import 가능한 패키지가 되는 것은 아니에요. 검색 경로와 패키지 구성 조건이 맞아야 합니다. 일반 패키지에서는 지금도 `__init__.py`가 의미가 있어요.

원문은 `chapter06/utils/sub/mod3.py`에서 `chapter06/mod1.py`의 `VERSION`을 가져오는 경로도 다룹니다. 다음은 `chapter06`을 패키지 루트로 import할 수 있게 구성했다고 가정한 비교예요. 원문에는 `mod2.multiply()` 구현이 없어 아래 코드는 경로 설명용이며 독립 실행할 수 없습니다.

```python
from chapter06.utils import mod2
result = mod2.multiply(10, 20)

from chapter06.utils.mod2 import multiply

# chapter06/utils/sub/mod3.py 안에서 쓰는 대안이에요.
from chapter06.mod1 import VERSION
# 같은 위치에서 상대 import로 표현하면 다음과 같아요.
from ...mod1 import VERSION
```

절대 import는 최상위 패키지 이름부터 적고, 상대 import는 현재 모듈이 속한 패키지를 기준으로 점을 사용해요. `.`은 현재 패키지, `..`은 부모 패키지, `...`은 그 위 패키지입니다. 원문의 `from ....chapter06.mod1. import VERSION`은 문법과 상대 경로가 맞지 않아 위 가정을 명시하고 수정했어요. 상대 import는 패키지 문맥이 필요하므로 해당 파일을 단독 스크립트로 실행하면 실패할 수 있습니다.

## 8. import 방식과 표준 라이브러리 정리

원문의 함수 트리는 별도의 날짜 문서로 만들지 않고 이 날짜 안에서 정리했어요. 기본 import 문법에서 동적 import와 코드 작성 관례까지 범위를 넓혀 둔 참고 메모이며, 노란색으로 표시된 수업 내용과 추가 정리 부분이 섞여 있습니다.

| 방식·도구 | 용도와 주의점 |
| --- | --- |
| `import math` | `math.sqrt(...)`처럼 출처를 드러내며 접근해요. |
| `import pandas as pd` | 모듈에 별칭을 붙여요. pandas는 별도 설치가 필요한 외부 라이브러리예요. |
| `from math import sqrt` | 필요한 이름만 가져와요. `sin, cos, tan`처럼 여러 이름도 지정할 수 있어요. |
| `from math import sqrt as sq` | 선택한 이름에 별칭을 붙여요. |
| `from module import *` | `__all__` 또는 공개 이름 규칙에 따라 이름을 가져와 충돌 위험이 있어요. |
| `from . import sibling_module` | 현재 패키지의 모듈을 가져와요. |
| `from ..utils import helper_func` | 부모 패키지 아래 경로를 기준으로 가져오는 형태예요. 실제 정의가 필요합니다. |
| `importlib.import_module("math")` | 문자열로 모듈을 지정해 동적으로 불러와요. |
| `__import__("math")` | import에 관여하는 저수준 내장 함수예요. 원문 트리에서 강조 문법으로 손상된 이름을 바로잡았습니다. |
| `sys.path` | 모듈을 검색하는 경로 목록이에요. 경로 추가는 검색 대상을 바꾸므로 무분별하게 수정하지 않아야 해요. |

와일드카드 import를 연속해서 사용하면 같은 이름이 뒤에서 가져온 이름으로 덮일 수 있습니다. 원문 예시의 `from math import *` 뒤에 `from numpy import *`를 쓰면 `sin`의 출처를 눈으로 추적하기 어려워져요. `module_a`, `module_b`, `module_c`에서 모두 `*`로 가져온 뒤 `fetch_payload()`를 호출하는 예제도 같은 가독성 문제를 보여줍니다. 해당 모듈들은 제공되지 않아 실행 코드로 꾸미지 않았어요.

> 바로잡기: `*` import가 객체를 전부 복제하거나 모든 내부 의존성을 반드시 새로 로드해 메모리가 크게 늘어난다는 설명은 부정확합니다. 주된 문제는 이름 공간 오염, 충돌, 출처 추적의 어려움이에요. `__all__`이 없으면 일반적으로 밑줄로 시작하지 않는 이름이 대상이며, 패키지 하위 파일을 자동으로 전부 탐색해 import하는 뜻도 아닙니다.

원문 트리에는 함수 안에서 필요한 시점에 import하는 지역·지연 import도 나옵니다. 함수 본문에 둔 import 문은 그 함수가 해당 줄에 도달했을 때 실행돼요. 다른 곳에서 이미 불러온 모듈이라면 캐시를 재사용할 수 있으므로 항상 그때 처음 로드된다는 뜻은 아닙니다.

PEP 8 관례로 정리한 부분은 표준 라이브러리, 외부 라이브러리, 프로젝트 내부 모듈 순서로 import를 묶고 그룹 사이에 빈 줄을 두는 방식이에요. `import os, sys`보다는 각 모듈을 한 줄씩 쓰되, `from math import sin, cos, tan`처럼 한 모듈의 여러 이름을 가져오는 문장은 가능합니다. 보통 파일 위쪽에 import를 모으지만, 필요에 따라 지연 import를 사용할 수 있어요.

순환 import는 모듈 A가 B를 불러오고 B가 다시 A를 불러오는 의존 구조입니다. 초기화가 끝나지 않은 모듈의 이름을 사용하다 오류가 생길 수 있어 공통 코드를 분리하는 등 의존 구조를 검토해야 해요. 모든 순환 import가 반드시 실패한다는 뜻은 아닙니다.

표준 라이브러리는 파이썬과 함께 제공되는 모듈·패키지 모음입니다. 모두 인터프리터에 내장된 모듈인 것은 아니에요. 원문에는 공식 문서에서 확인할 수 있다는 안내만 있고 상세 모듈 목록은 없어 덧붙이지 않았습니다.

## 9. 기록 범위와 출처

LEGB·전역변수 복습, 람다·`map`·`filter`, 이터러블·이터레이터·`StopIteration`, 제너레이터와 표현식, 동기·비동기 비교, 모듈·패키지·별칭·초기화·import 캐시·상대 경로·와일드카드·동적 import·표준 라이브러리를 반영했어요. 빈 회고와 기본 탭은 제외했습니다. 제공된 번들에서 확인할 수 없는 이미지 내용은 추정하지 않았고, 이미지가 있었다면 원문에서 확인해야 합니다. 만료되는 이미지 URL은 포함하지 않았어요.

예제의 파이썬 문법을 검사하는 것과 실제 파일 배치·패키지 import·외부 라이브러리 동작을 검증하는 것은 달라요. 여기서는 학습용 코드와 불완전한 파일 구성 예시를 구분했으며, 실제 실행·네트워크 접근·성능 측정은 하지 않았습니다.
